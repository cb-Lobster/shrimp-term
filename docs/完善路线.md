# shrimp-term · 现状体检与完善路线

> 体检时间：2026-10-29 ｜ 代码版本：`main` 分支（0.0.1）
> 结论：**底子可用，方向明确——它不该只是"终端"，而应该是"终端 + 运维助手"，并补一个服务端才算全栈。**

---

## 0. 终态长什么样（先看终点，再看路线）

**一句话**：一个能在 Windows 上安装、登录账号后跨设备同步主机配置、连上机器后助手能看着终端输出帮你判断、危险动作必须你点确认才会执行的桌面运维工具。

**一次真实使用**
> 周五凌晨群里说 B 机站挂了。打开 shrimp-term → 主机列表里 B 机磁盘标红 → 双击连上 → 终端里 `502` 一直刷 →
> 点右侧助手："这台为什么 502？" → 助手已读到当前主机和最近 200 行输出，回"后端进程已退出，反代正常，日志显示连 3306 被拒" →
> 建议"重启 blog-api"，点"预览"看它要执行什么 → 点确认 → 执行 → 自动复检返回 200 → 记一条审计。
> 第二天换台电脑打开，主机、分组、这次历史都还在。

**三个可交付节点**

| 节点 | 交付物 | 一句话 |
|---|---|---|
| v0.2 | 能发给朋友安装的终端 | 有安装包、有 Release、有 README 截图 |
| v0.3 | 有助手、敢用的终端 | 三闸门 + 四段式，危险动作强制确认（**差异化**） |
| v1.0 | 有账号、能同步的终端 | 后端 + 数据库 + JWT + 部署，**这才是全栈** |

**它不做**：多人团队协作、Web 端多机编排（那是 Astral 的地盘）、CI/CD 流水线管理。

## 二、产品定位（一句话）

> **shrimp-term 是一个本地 SSH 终端，内置一个"不敢乱来"的运维助手：你连上机器，它看得见终端输出，能诊断、能建议，危险动作必须你点确认。**

### 和 Astral 的区别（重要，面试要能讲）

| | Astral | shrimp-term |
|---|---|---|
| 形态 | Web 平台 + 多机控制面 | **本地桌面终端** |
| 执行位置 | 远端电脑上的 agent | **你自己正在连的那台机器** |
| 能力面 | 任意命令 | 终端里能做的 + 白名单动作 |
| 价值 | 一人管多机 | **把"手敲命令 + 查资料"合成一步** |

**不要去追 Astral。** 它的优势是"多机编排"，你的优势是"人就在终端前，上下文天然在手里"。

## 四、助手现在的短板（为什么它还不算"运维助手"）

从通道名看，`agent:ask` 是"问一句 → 回一句"。缺三样：

1. **没有上下文**：不知道当前连的是哪台机器、终端里刚报了什么错；
2. **没有纪律**：可以建议任何命令，但没人保证它不让你 `rm -rf`；
3. **没有闭环**：给了建议就结束，不检查结果。

第 1 条靠 `term:open` 时把主机信息 + 输出缓冲传给助手；第 2、3 条靠三闸门与复检。这三样做完，它才配叫 "ops agent built in"。

## 五、要全栈，必须补服务端（三选一）

**核心判断**：Electron 是客户端。面试官问"你的服务端在哪、数据怎么存、怎么鉴权"，只有本地 JSON 是答不上的。

| 方案 | 功能 | 需要的技术 | 工作量 | 面试价值 |
|---|---|---|---|---|
| **A. 配置云同步**（推荐先做） | 账号登录；主机/分组/历史跨设备同步 | Postgres + JWT + REST + 冲突处理 | 1—2 周 | ⭐⭐⭐ 最小完备闭环 |
| B. 团队共享主机 + 权限 | 组织/成员；谁能连哪台、能做什么 | RBAC、审计、组织模型 | 2—3 周 | ⭐⭐⭐ 更贴 B 端 |
| C. 会话录制与审计回放 | 全量录制、按时间回放、关键字检索 | 流式存储、分段、检索 | 3—4 周 | ⭐⭐ 技术含量高 |

### 推荐路径：A → B

**A 的最小实现（建议两周内跑通）**
1. 后端：FastAPI 或 Node(Express/Fastify) + PostgreSQL + JWT
2. 四张表：`users` / `devices` / `hosts` / `sync_log`
3. 接口：注册登录、`GET/POST /hosts`、`POST /sync`（增量）、`GET /sync?since=`
4. 冲突策略：以 `updated_at` 后写为准 + 客户端保留本地副本（离线可用）
5. 部署：Docker Compose（后端 + PG）+ Nginx + HTTPS
6. CI：GitHub Actions 跑 lint + 测试 + 构建

**为什么选 A 不选 C**：A 用最少的功能逼你把"表设计、鉴权、API、部署"各走一遍；C 技术漂亮但战线太长，简历上不加分更多。

## 六、全栈面试会被问到的（提前准备）

| # | 问题 | 你要准备到 |
|---|---|---|
| 1 | 客户端和服务器怎么同步？ | 增量 vs 全量、冲突判定（时间戳/Lamport）、离线队列 |
| 2 | 数据怎么建模？ | 为什么 hosts 与 devices 分开、索引加哪、软删除 |
| 3 | 鉴权怎么做？ | JWT 存放位置、刷新、Electron 下用 `safeStorage` 存 token |
| 4 | 密钥怎么存？ | 绝不明文；`safeStorage` + 系统凭据库；服务端存哈希或加密 |
| 5 | 怎么部署？ | Compose 编排、反代、TLS、环境变量、回滚 |
| 6 | Electron 的安全要点？ | `contextIsolation`、禁用 `nodeIntegration`、只通过 preload 暴露白名单 API、校验 IPC 入参 |
| 7 | 怎么做测试？ | 单测（纯函数/IPC 校验）、集成（同步接口）、E2E（Playwright + Electron） |
| 8 | 讲一次排查经历 | 用真实 bug（比如中文乱码、xterm 尺寸、SSH 断线重连）讲清定位过程 |
